# 진동계 Cat 송신 중단 — 조사 노트

> 적립용 문서. 대화·현장 단서를 모으며 갱신한다.  
> 최종 갱신: 2026-08-06 (1NCE 글로벌 유심 확정)

---

## 1. 한 줄 결론 (현재)

- Convert의 **정상 변환(원본 읽기)** 만으로 로거 Cat 송신이 끊길 구조는 약하다.
- 증상(원본 실측 중단 + 로거 “안 보냄” + **대별·비동시** 끊김)은 **기기 단위 통신/펌웨어 복구** 쪽이 유력하다.
- 원격 재부팅은 **로거가 한 번이라도 HTTP POST할 때만** 가능. 이미 무송신이면 원격 불가 → 현장 USB/전원.

## 2. 시스템 사슬 (역할 분리)

```
센서 → 로거 펌웨어 → Cat 모뎀 → 망/유심 → 수신 서버(htdocs save_data)
    → 원본 CSV → Convert(변환본) → 포털/모니터링
```

| 구성 | 명칭 | 역할 |
|------|------|------|
| 현장 박스 | 로거(데이터 로거) + 센서(진동계) + 모뎀 | 샘플·집계·무선 송신 |
| 기기 안 SW | **펌웨어** (`.bin`은 배포물, 소스 아님) | 초당 샘플 → 주기 max → Cat 송신 |
| 수신 | `htdocs` / `save_data.py` 등 | POST 수신 → CSV/hex 저장, 응답에 명령 가능 |
| PC SW | Convert Pro 3 | 원본 읽기 → 변환본 저장 (Cat 제어 없음) |
| 설정 툴 | `6.펌웨어/code` QM Data Logger Manager | USB 시리얼 AT, 모뎀 설정, 펌 안내 |

## 3. 증상 (합의된 사실)

- 원본에 **실측 행이 더 이상 안 들어옴**.
- 현장 확인 시 로거는 **전원 ON**, “**안 보냈다**”는 쪽.
- **동시 전멸이 아니라 대별로 하나씩** 끊김 → 서버/Convert 일괄 장애 가능성 ↓, **기기·유심·펌 상태** ↑.
- 원격으로 접속·재부팅이 안 됨 = **송신(POST)이 이미 죽은 뒤**라 명령을 실을 응답 채널이 없음.

## 4. Convert / SW 쪽 — 남길 것 / 버릴 것

### 유지 (참고)

| 항목 | 내용 |
|------|------|
| 일반 변환 | 원본 `rb` 공유 읽기, 쓰기는 변환본. exclusive lock로 Cat을 끊는 구조 아님 |
| `PermissionError` | 재시도 후 **스킵** (로거를 풀어주지 않음) |
| `__gen_interval__` | **원본 CSV를 통째로 다시 씀** → 수신과 충돌 잠재 위험 (문서 `POTENTIAL_ISSUES`에도 있음). 다만 “안 보냄”의 주원인으로 단정하지 않음 |
| `htdocs` 응답 | POST 성공 시 `sendPeriod` / `reset` 등 JSON 응답 가능 → **아직 살아 있는 기기**에만 유효 |
| 매니저 기본 | 예: APN `iot.1nce.net`, `AT-SAMPLE_TIME` 기본 600초, Quectel 계열 탐지, Nuvoton ISP 플래시 안내 |

### 소거 (이 이슈에서 주요 원인 아님)

- “변환 횟수가 많아서 파일 점유로 Cat이 멈춘다” (기본 경로 근거 약함)
- 주기생성 0행 = 로거가 0을 송신했다
- Convert로 펌웨어 수정/원격 로거 재부팅
- `.bin`만으로 소스 복원·로직 수정
- “처음부터 펌 자작” (현실적 대안 아님; 협력사 소스·패치)
- 큐엠원격모니터링 = 현장 로거 SSH/원격 재부팅 (PC/서버 쪽)

## 5. 유력 가설 (우선순위)

1. **펌웨어**: 망/송신 실패 후 **재시도·망 재등록 없이 고착** (하나씩 죽음과 잘 맞음)
2. **통신/유심**: **이번 끊김 대상은 통신사(국내 MNO) 유심**. 1NCE(글로벌)는 **다른 장비용** → 이번 가설에서 소거에 가깝게 둠
3. **모뎀/RF**: 세션·신호·Deep sleep 후 미복구 (`Deep_sleep:1` 비트는 추가 확인 필요)
4. **보조**: `__gen_interval__`와 수신 동시 write (별도 검증; 주원인 후보에서 후순위)

## 5-1. 유심 — 정정

| 구분 | 내용 |
|------|------|
| **이번 진동계 끊김** | **통신사 유심** (글로벌/1NCE 아님) |
| **1NCE** (`portal.1nce.com`) | **다른 장비용**. 이번 케이스 원격 매칭·사용량 조회 수단 아님 |
| 파일명 `1222527837` | 로거 `lineNumber`. **현재 어떤 유심 포털과도 자동 매칭 수단 없음** |

### 통신사 유심일 때

- 통신사 IoT/회선 포털 권한이 있으면: 회선 상태·사용량·최종 통신 조회 (1NCE와 같은 역할)
- 권한·매핑 없으면: 파일명만으로 유심 상태 원격 조회 **불가** → 개통 대장 또는 현장 ICCID/IMEI
- 글로벌 유심 로밍 가설은 **이번 대상에서 소거**. **국내망·Cat.M1·펌 복구**에 집중

### 사용량 판독 논리 (통신사 포털에도 동일)

| 유심 측 | 원본 실측 | 해석 |
|---------|-----------|------|
| 끊긴 뒤 **무트래픽** | 끊김 | 기기→망 송신 중단 |
| **트래픽 있음** | 원본만 끊김 | 서버·수신 쪽 |
| 정상 회선과 비교 | — | 전체 vs 그 대만 |

### (참고) 1NCE — 다른 장비

- APN `iot.1nce.net`, 포털 MSISDN `88228…` ≠ 파일 회선번호
- 목록에서 `1222527837` 검색 안 됨

## 5-2. 구조적 한계: 로그는 현장에 / 현장은 지하철

협력사(개발) 측 요청: **문제 재현·수정을 위해 로그 필요**.  
현실: 로그는 **USB 시리얼**이 주 경로 → **지하철 현장 출입·보고** 후에야 채취 가능.

```
통신 OK  → 원격 가능 / 이때는 안 보냄이 아님
통신 끊김 → 원격·원격 로그 불가 → 현장만 / 출입 비용 큼
```

관측 수단이 고장 모드와 같은 채널(Cat HTTP)에만 묶여 있으면, 로그 가져와 고친다가 구조적으로 막힌다.  
**통신이 되면 문제는 없고, 문제일 때는 로그 경로도 같이 죽는다.**

### 구조 개선 방향 (협력사·차기 펌)

| 개선 | 요지 |
|------|------|
| **로컬 블랙박스** | 실패·CSQ·CEREG·HTTP를 비휘발 링버퍼. 현장 USB로 짧게 dump |
| **성공 시 진단 조각** | 살아 있을 때 POST에 lastError/csq 등 |
| **보조 채널(선택)** | SMS 등으로 에러코드만 |
| **회선 매핑표** | `lineNumber` ↔ ICCID/IMEI/통신사 회선 (사무실 조회용) |

사무실에서 할 수 있는 것: 원본 실측 마지막·기기별 패턴 표. 통신사 포털·매핑이 있으면 사용량 대조. (완전 로그 대체는 아님)

## 6. 펌웨어 폴더 (`6.펌웨어`) 요약

- 제품별 `.bin` 배포물. 진동 배터리 예:
  - `…电池版10分钟6次上报…` (10분·6회 보고 추정)
  - `Firmware_QM_ACC_LED_LP_…` (ACC+저전력)
- 바이너리: 문자열/AT 거의 없음, 고엔트로피 → **암호화·패키지**. 까서 수정 불가.
- 업데이트: USB + Nuvoton ISP (TEST+RESET). 매니저는 파일 선택 안내 수준.
- 수정·재빌드: **협력사 소스** 필요. 현재 소스 미수령.

## 7. 원격 reset이 되는 조건 / 안 되는 조건

```
로거 POST → save_data 응답에 reset/sendPeriod → 펌이 해석(가정)
POST 없음 → 원격 명령 경로 없음 → 현장만 가능
```

응급용일 뿐 **근본 수정 아님**.
